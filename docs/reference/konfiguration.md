# Konfiguration

## Dateien

| Pfad | Inhalt |
| --- | --- |
| `$XDG_CONFIG_HOME/flakipype/config.toml` (Standard `~/.config/flakipype/config.toml`) | Die Einstellungen unten; enthält nie Secrets |
| `$XDG_CONFIG_HOME/flakipype/secrets.json` | Der API-Key bei `secrets.store = "file"`, oder bei `"auto"` auf Rechnern ohne System-Keyring; Modus `0600` |
| `$XDG_DATA_HOME/flakipype/bin/gh` (Standard `~/.local/share/flakipype/bin/gh`) | Von flakipype heruntergeladenes `gh` |
| `$XDG_DATA_HOME/flakipype/cache.sqlite3` | Scan-Cache (Jobs abgeschlossener Versuche, Log-Signaturen, geprüfte Urteile und was Läufe sich merken: nicht gepushte Korrekturen, Untersuchungen ohne Urteil), Chat- und Lauf-Sitzungen und das Audit-Protokoll der Aktionen; wer ihn löscht, löscht auch die Sitzungen und das Protokoll |
| `$XDG_DATA_HOME/flakipype/run.lock` | Von einem laufenden `flakipype run` gehalten, damit immer nur einer läuft |
| `$XDG_CONFIG_HOME/systemd/user/flakipype.{service,timer}` | Von `flakipype daemon install` geschrieben, markiert mit `generated by flakipype` |

Relative `XDG_*`-Werte werden ignoriert, wie es die XDG-Spezifikation
verlangt.

## `config.toml`

```toml
[llm]
base_url = "https://api.anthropic.com"
model = "claude-sonnet-4-5"

[github]
host = "github.com"
owner = "octo-org"

[scan]
window_days = 30
max_log_downloads = 50
max_job_reads = 500
min_flaky_runs = 2

[agent]
max_rounds = 12
max_tokens_per_investigation = 200000
max_seconds_per_investigation = 300
max_tokens_per_run = 1000000
parallel = 3
max_output_tokens = 16000
thinking = "adaptive"
thinking_budget = 8000
excerpt_lines = 120

[actions]
max_per_session = 10
max_watched = 10
watch_hours = 6

[fix]
max_prs_per_session = 3
max_files = 10
max_changed_lines = 400
verify_runs = 3
max_rounds = 20
max_tokens = 300000
max_seconds = 600

[run]
max_minutes = 120
max_prs_per_day = 3
max_actions_per_day = 20
max_tokens_per_day = 3000000

[secrets]
store = "auto"
```

| Schlüssel | Standard | Regeln |
| --- | --- | --- |
| `llm.base_url` | `https://api.anthropic.com` | `https://`; `http://` nur für `localhost`, `127.0.0.1`, `::1`. Ein Host, der auf `.services.ai.azure.com` endet, nutzt den Azure-AI-Foundry-Client. Ein abschließender Schrägstrich wird entfernt. |
| `llm.model` | — (Pflicht) | Modellname; auf Foundry der Deployment-Name |
| `github.host` | `github.com` | Hostname ohne Schema, z. B. `github.example.com` für GitHub Enterprise Server |
| `github.owner` | — (Pflicht) | Name des GitHub-Benutzers oder der Organisation |
| `scan.window_days` | `30` | 1–400 Tage, die zurückgeschaut wird (GitHub hält die Lauf-Historie 400 Tage, Logs meist 90) |
| `scan.max_log_downloads` | `50` | 0–1000; festes Limit der Job-Logs, die pro Scan gelesen werden. Gelesene Logs werden gecacht, spätere Scans machen also weiter |
| `scan.max_job_reads` | `500` | 0–5000; festes Limit der Versuche, deren Jobs pro Scan gelesen werden, Kandidaten für Instabilität und neueste zuerst. Gelesene Jobs werden gecacht, spätere Scans machen also weiter |
| `scan.min_flaky_runs` | `2` | 1–100; Läufe mit nachgewiesenen Flake-Ereignissen, bevor ein Job als instabil gilt (und bevor ein Fehler als wiederkehrend gilt). Mit `1` zählt jedes einzelne Ereignis |
| `agent.max_rounds` | `12` | 1–50 Modellaufrufe pro Untersuchung |
| `agent.max_tokens_per_investigation` | `200000` | 10k–2M Tokens (Eingabe, Ausgabe, Cache-Schreib- und -Lesezugriffe mit vollem Gewicht, Thinking) pro Untersuchung; auch pro Chat-Frage, wobei nur zählt, was die Frage hinzufügt |
| `agent.max_seconds_per_investigation` | `300` | 30–3600 |
| `agent.max_tokens_per_run` | `1000000` | 10k–20M für alle Untersuchungen eines `investigate`-Laufs; ist es erreicht, starten keine neuen mehr |
| `agent.parallel` | `3` | 1–8 Untersuchungen gleichzeitig (GitHub-Aufrufe gehen weiterhin einzeln nacheinander) |
| `agent.max_output_tokens` | `16000` | 1k–64k pro Modellaufruf; Aufrufe werden gestreamt, daher funktioniert der ganze Bereich |
| `agent.thinking` | `adaptive` | `adaptive`, `enabled` (nutzt `thinking_budget`) oder `off`. Neuere Modelle akzeptieren nur `adaptive`; die anderen sind für ältere Modelle |
| `agent.thinking_budget` | `8000` | 1.024–60k; nur mit `thinking = "enabled"`, muss dann unter `max_output_tokens` liegen |
| `agent.excerpt_lines` | `120` | 20–400 Zeilen in einem Log-Auszug |
| `actions.max_per_session` | `10` | 1–100 Reruns und Dispatches pro Chat-Sitzung (jede Wiederholung eines Dispatches zählt); `/new` beginnt eine neue Zählung |
| `actions.max_watched` | `10` | 1–50 gestartete Läufe, die gleichzeitig beobachtet werden |
| `actions.watch_hours` | `6` | 1–24 Stunden, die ein gestarteter Lauf abgefragt wird, bevor der Chat ihn nicht mehr beobachtet |
| `fix.max_prs_per_session` | `3` | 1–20 Draft-PRs pro Chat-Sitzung; `/new` beginnt eine neue Zählung |
| `fix.max_files` | `10` | 1–50 geänderte Dateien pro Korrektur |
| `fix.max_changed_lines` | `400` | 10–2.000 hinzugefügte plus entfernte Zeilen pro Korrektur |
| `fix.verify_runs` | `3` | 1–10 Läufe des Workflows auf dem Branch der Korrektur; die Reruns zählen gegen `actions.max_per_session` |
| `fix.max_rounds` | `20` | 5–60 Modellaufrufe des Fixers |
| `fix.max_tokens` | `300000` | 10k–2M Tokens für den Fixer und seinen Reviewer zusammen |
| `fix.max_seconds` | `600` | 60–3600 Sekunden für den Fixer |
| `run.max_minutes` | `120` | 10–720 Minuten, die ein `flakipype run` dauern darf; danach startet keine Untersuchung und keine Korrektur mehr, und eine Korrektur bekommt höchstens die verbleibende Zeit. Das eigene Limit der systemd-Unit liegt bei 730 Minuten, egal, was hier eingestellt ist |
| `run.max_prs_per_day` | `3` | 1–20 Draft-PRs, die alle Läufe der letzten 24 Stunden öffnen dürfen |
| `run.max_actions_per_day` | `20` | 1–200 Reruns und Dispatches, die alle Läufe der letzten 24 Stunden starten dürfen |
| `run.max_tokens_per_day` | `3000000` | 10k–50M Tokens, die alle Läufe der letzten 24 Stunden verbrauchen dürfen |
| `secrets.store` | `auto` | `auto` (der System-Keyring, oder `secrets.json`, wo es keinen gibt), `keyring` oder `file` |

In einem Lauf sind `fix.max_prs_per_session`, `actions.max_per_session` und
`agent.max_tokens_per_run` die Limits dieses einen Laufs, und Untersuchungen
und Korrekturen teilen sich das Token-Limit.

Unbekannte Schlüssel sind ein Fehler, damit ein Tippfehler nie unbemerkt
bleibt. `flakipype setup` bearbeitet nur `[llm]`, `[github]` und
`secrets.store` und lässt jeden anderen Abschnitt so, wie er in der Datei
steht. Ungültige Werte in den Abschnitten, die es bearbeitet, ersetzt es; es
verweigert aber das Speichern und nennt den Fehler, wenn die Datei kein
gültiges TOML ist oder ein anderer Abschnitt ungültig ist: Diese korrigierst
du von Hand, die Einrichtung setzt sie nie auf die Standardwerte zurück.

## Secrets

| Name | Wo |
| --- | --- |
| LLM-API-Key (`llm-api-key`, Dienst `flakipype`) | `secrets.store`: System-Keyring über `keyring` (Secret Service, KWallet, …) oder `secrets.json` |
| GitHub-Token | Nicht von flakipype gespeichert: Es ist die eigene Anmeldung von `gh` (`gh auth login`) |

Ein gesperrter oder nicht erreichbarer Keyring, typischerweise unter einem
systemd-Timer ohne Desktop-Sitzung, wird mit Exit-Code 2 und dem nächsten
Schritt gemeldet:
`flakipype setup --non-interactive --secret-store file --api-key-stdin`.
`secrets.json` wird als Ganzes über eine temporäre Datei ersetzt, sodass ein
fehlgeschlagener Schreibvorgang (volle Festplatte) die vorherige Datei
behält.

## gh

flakipype nutzt der Reihe nach:

1. `gh` im `PATH`, wenn es Version 2.97.0 oder neuer ist;
2. seine eigene Kopie in `$XDG_DATA_HOME/flakipype/bin/gh`.

2.97.0 ist die erste Version, die Terminal-Escape-Sequenzen in der Ausgabe von
`gh api` neutralisiert und `--allow-escape-sequences` anbietet, das der Scan
braucht, um rohe Job-Logs zu lesen (flakipype entfernt sie dann selbst).

flakipype startet `gh` ohne die von WSL eingebundenen Windows-Ordner
(`/mnt/c/…`) im `PATH`: Sie zu durchsuchen machte jeden Start von `gh` etwa
eine Sekunde langsamer.

Gibt es keins von beiden, lädt `flakipype setup` das neueste
`cli/cli`-Release für den Rechner herunter (`amd64`, `arm64`, `armv6`, `386`),
prüft das Tarball gegen die `gh_<version>_checksums.txt` des Releases und
installiert es atomar. Bei einer Abweichung bricht es ab und installiert
nichts.

Der Download nutzt nur URLs auf `github.com`, nie `api.github.com`: Die
neueste Version wird aus der Weiterleitung von
`github.com/cli/cli/releases/latest` gelesen. Nicht authentifizierte
API-Aufrufe sind auf 60 pro Stunde und IP-Adresse begrenzt, was Benutzer
hinter einer gemeinsamen Firmenadresse schnell aufbrauchen. Lehnt GitHub
trotzdem ab (HTTP 403 oder 429), sagt die Einrichtung das und schlägt vor,
`gh` stattdessen von <https://cli.github.com> zu installieren.

Nötige Token-Scopes für klassische und OAuth-Tokens: `repo`, `workflow`,
`read:org` (`write:org` oder `admin:org` erfüllen `read:org` ebenfalls).
